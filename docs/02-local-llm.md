# 02. ローカルLLM運用

コンシューマGPUで大規模MoEモデルを実用的な速度で動かすための記録です。

## 構成

| 項目 | M1 | M2 |
|---|---|---|
| GPU | RTX 3060 12GB | RTX 3080 10GB |
| RAM | 64GB | 64GB |
| CPU | Threadripper 2990WX (32C/64T) | Threadripper 1920X (12C/24T) |
| モデル | 125B MoE (UD-Q2_K_XL) | 同左 |
| コンテキスト | 256K | 128K |
| KV量子化 | Q8_0 | Q4_0 |
| 生成速度 | 10.8〜11.0 t/s | 11.2〜11.7 t/s |
| プリフィル | 110〜120 t/s | 175〜184 t/s |

ランナーは `llama.cpp` のサーバー（OpenAI互換API）。

## なぜ 125B を 12GB で動かせるのか

MoE（Mixture of Experts）は、推論時に**一部のエキスパートしか活性化しません**。
そのため、モデル全体はRAMに置き、活性化する層だけをGPUに載せる形が成立します。

```bash
llama-server \
  -m model-00001-of-00003.gguf \
  -ngl 99 -cmoe \
  -c 262144 \
  -ctk q8_0 -ctv q8_0 \
  -fa on --jinja \
  -t 32 -b 8192 -ub 2048 \
  --reasoning-effort xhigh
```

| フラグ | 役割 |
|---|---|
| `-ngl 99` | 可能な限りGPUにオフロード |
| `-cmoe` | MoEのエキスパートをCPU側に残す |
| `-ctk/-ctv` | KVキャッシュの量子化（K/V個別指定） |
| `-fa on` | Flash Attention |
| `-ub` | 物理バッチサイズ（後述のクラッシュ要因） |

## 最大の発見：KV量子化を混ぜると壊れる

RAMを節約するため、KをQ8_0、VをQ4_0にする「混在量子化」を試しました。
結果は**長文脈で0.70 t/s**。同一量子化なら10.84 t/sです。**15倍の差**が出ました。

原因はFlash Attentionの無効化でした。混在指定にするとFAが有効に働かず、
文脈長に比例して急激に遅くなります。

```
K=q8_0 / V=q8_0  →  4K文脈 10.84 t/s   （FA有効）
K=q8_0 / V=q4_0  →  4K文脈  0.70 t/s   （FA無効）
```

**教訓：KVキャッシュの量子化は、必ずKとVで同じ方式を指定する。**

この挙動はエラーも警告も出ません。「なんとなく遅い」という症状だけが出るため、
ベンチマークを取っていなければ原因に辿り着けませんでした。

## 2つ目の発見：`ub=2048` でクラッシュする

プロンプトが約1,600トークンを超えると、CUDAの不正メモリアクセスで
GPUが15分間ハングする現象が発生しました。

再現条件を追い込んだ結果、`-ub 2048`（物理バッチ）が原因と特定。

| 入力トークン | `ub=2048` | `ub=1024` |
|---|---|---|
| ≤1,581 | 成功 | 成功 |
| ≥1,602 | **クラッシュ** | 成功 |

`-ub 1024` に分割すると、同じビルドでも安定します。
クラッシュの閾値がトークン数で再現性100%だったため、切り分けは比較的早く終わりました。

## メモリの実測

| 状態 | VRAM | RAM |
|---|---|---|
| 256K / Q8_0 KV | 11.6GB / 12GB | 53〜55GB |
| 128K / Q4_0 KV | 9.3GB / 10GB | ― |

FP16のKVキャッシュは256KではRAMが不足します。Q8_0にすると品質はほぼ無劣化で、
約5GB節約できました。

## 品質のA/Bテスト

量子化による品質劣化を感覚で判断しないため、5種類のプロンプトで自動採点しています。

| 種別 | 検査内容 |
|---|---|
| reasoning | 古典的な文章題（正答 `0.05` を機械判定） |
| code | 制約付きの関数生成（`sorted()` 不使用を機械判定） |
| ja_polite | 日本語の丁寧語変換（禁止語の混入を検査） |
| summarize | 3箇条の要約（箇条書き数を数える） |
| longctx_needle | 長文中の特定文字列の保持（ニードルテスト） |

`src/llm/benchmark.py` に一般化した実装があります。

```bash
python -m src.llm.benchmark --base-url http://127.0.0.1:8080 --model my-model --quant q8_0
```

## 運用で踏んだ罠

### タスクスケジューラの72時間制限

Windowsのタスクスケジューラは、既定で **72時間** を超えるとプロセスを強制終了します。
3日ごとに推論サーバーが黙って落ちる原因がこれでした。

対策：`ExecutionTimeLimit` を `PT0S`（無制限）に変更し、失敗時の自動再起動を設定。
`schtasks /Change` では変更できず、`Set-ScheduledTask -Settings` が必要です。

### SSH経由で起動したプロセスはセッション終了で死ぬ

`ssh host "start server"` で起動しても、SSHセッションが切れた瞬間に子プロセスが殺されます。
常駐させるには、タスクスケジューラかサービス経由で**プロセスを切り離す**必要があります。

### 「応答がない」の正体は低速化

サーバーが落ちていると思ったら、生きていて**生成速度だけが半分以下**に落ちていました。
GPUのサーマルスロットルもなく、競合プロセスもなし。
最終的に**マシンのリブートで復旧**しました。経時的なOS/ドライバ状態の劣化と考えられます。

対策：死活監視だけでなく、**定期的にスループットを測る**。
「動いている」と「使える」は別です。

## この構成の限界

- 125Bモデルは12GBでは厳しく、Q2量子化による品質劣化は避けられない
- プリフィルが110 t/sなので、長い文書の投入は遅い
- 単機のGPUメモリがボトルクなので、モデルを大きくすると即座に破綻する

次にやるなら、**量子化をQ4以上に上げるためにGPUメモリを増やす**か、
**プリフィルをGPU側に寄せる**構成にします。
